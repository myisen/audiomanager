# Oracle Row-Level Security (Virtual Private Database)

## Overview

Virtual Private Database (VPD / Fine-Grained Access Control) enforces row-level security inside the Oracle kernel: every SQL statement touching a protected table is transparently rewritten to append a `WHERE` predicate generated by a PL/SQL policy function — before the optimizer sees the query. Unlike application-layer filtering, VPD cannot be bypassed by ad-hoc queries, ETL tools, or reporting applications. VPD is an Enterprise Edition feature, widely used for multi-tenant SaaS, HIPAA, and SOX workloads.

## Architecture

```
Application sends:   SELECT * FROM hr.employees
VPD rewrites to:     SELECT * FROM hr.employees
                     WHERE department_id IN (SELECT ... WHERE username =
                       SYS_CONTEXT('USERENV','SESSION_USER'))
The rewritten query is what actually executes.
```

Components: an **application context** (namespaced session attributes, settable only by a trusted package), a **policy function** (`VARCHAR2(schema, object) → predicate string`), and the **policy** registered via `DBMS_RLS.ADD_POLICY`.

## Application Context

> **Operational — preconditions / risk / confirm:** logon triggers execute on every login — an unhandled error blocks logins, so swallow-and-log deliberately. Grant `CREATE CONTEXT` only to security administrators.

```sql
-- Context namespace; the USING package is the only thing allowed to set values
CREATE OR REPLACE CONTEXT hr_security_ctx USING hr.set_context_pkg;

CREATE OR REPLACE PACKAGE BODY hr.set_context_pkg AS
  PROCEDURE set_user_context IS
    v_dept_id NUMBER; v_user_role VARCHAR2(30);
  BEGIN
    SELECT e.department_id, e.job_id INTO v_dept_id, v_user_role
    FROM   hr.employees e
    WHERE  e.email = SYS_CONTEXT('USERENV', 'SESSION_USER');
    DBMS_SESSION.SET_CONTEXT('hr_security_ctx', 'dept_id',   v_dept_id);
    DBMS_SESSION.SET_CONTEXT('hr_security_ctx', 'user_role', v_user_role);
  EXCEPTION
    WHEN NO_DATA_FOUND THEN   -- non-employees: deny-by-default values
      DBMS_SESSION.SET_CONTEXT('hr_security_ctx', 'dept_id',   '-1');
      DBMS_SESSION.SET_CONTEXT('hr_security_ctx', 'user_role', 'NONE');
  END;
END;
/

-- Most reliable population path: database logon trigger
CREATE OR REPLACE TRIGGER hr.set_logon_context
  AFTER LOGON ON DATABASE
BEGIN
  IF SYS_CONTEXT('USERENV', 'SESSION_USER') NOT IN ('SYS', 'SYSTEM') THEN
    hr.set_context_pkg.set_user_context;
  END IF;
EXCEPTION WHEN OTHERS THEN NULL;  -- never block login; log instead
END;
/
```

Read values with `SYS_CONTEXT('hr_security_ctx', 'dept_id')`; the built-in `USERENV` namespace provides `SESSION_USER`, `IP_ADDRESS`, `MODULE`, `ISDBA`, `HOST`, `CURRENT_SCHEMA`, and more.

## Policy Functions

The signature is fixed: `(p_schema VARCHAR2, p_object VARCHAR2) RETURN VARCHAR2`. Returning `NULL` means no restriction (all rows); returning `'1=0'` means no rows. Missing context must mean deny.

```sql
CREATE OR REPLACE FUNCTION hr.emp_dept_policy(
  p_schema VARCHAR2, p_object VARCHAR2) RETURN VARCHAR2 AS
BEGIN
  CASE SYS_CONTEXT('hr_security_ctx', 'user_role')
    WHEN 'HR_MGR' THEN   -- managers: own department only
      RETURN 'department_id = ' || SYS_CONTEXT('hr_security_ctx', 'dept_id');
    WHEN 'HR_DIR' THEN
      RETURN NULL;       -- directors: all rows
    ELSE                 -- everyone else: own record only
      RETURN 'email = SYS_CONTEXT(''USERENV'', ''SESSION_USER'')';
  END CASE;
END;
/
```

Multi-tenant variant: if the tenant context is NULL, return `'1=0'` (deny) — unless `SYS_CONTEXT('USERENV','ISDBA') = 'TRUE'`, which is a deliberate, documented bypass.

## Registering Policies

> **Operational — preconditions / risk / confirm:** policies apply to new statements immediately and affect every user, including batch jobs — test with representative accounts before enabling on production tables.

```sql
BEGIN
  DBMS_RLS.ADD_POLICY(
    object_schema   => 'HR',
    object_name     => 'EMPLOYEES',
    policy_name     => 'EMP_DEPT_VISIBILITY',
    function_schema => 'HR',
    policy_function => 'EMP_DEPT_POLICY',
    statement_types => 'SELECT, INSERT, UPDATE, DELETE',
    update_check    => TRUE,   -- prevent UPDATE/INSERT moving rows out of scope
    enable          => TRUE);
END;
/
```

Key parameters: `statement_types` (`SELECT/INSERT/UPDATE/DELETE/INDEX`), `update_check`, `static_policy`/`policy_type`, `long_predicate` (up to 32KB predicates), `sec_relevant_cols` + `sec_relevant_cols_opt`.

## Policy Types (Performance-Critical)

- `DBMS_RLS.STATIC` — function called once, result cached for the policy lifetime; highest performance; for fixed predicates like `status != 'DELETED'`.
- `DBMS_RLS.CONTEXT_SENSITIVE` — re-evaluated when the application context changes; best for app-context multi-tenancy.
- `DBMS_RLS.DYNAMIC` (default) — called on every query; most flexible, avoid on high-frequency tables.

```sql
BEGIN
  DBMS_RLS.ADD_POLICY(
    object_schema   => 'SAAS', object_name => 'CUSTOMER_DATA',
    policy_name     => 'TENANT_ISOLATION',
    function_schema => 'SAAS', policy_function => 'TENANT_ISOLATION_POLICY',
    statement_types => 'SELECT, INSERT, UPDATE, DELETE',
    update_check    => TRUE,
    policy_type     => DBMS_RLS.CONTEXT_SENSITIVE);
END;
/
```

## Column Masking (sec_relevant_cols_opt)

Return rows with NULL in sensitive columns for unauthorized users, instead of hiding the rows:

```sql
BEGIN
  DBMS_RLS.ADD_POLICY(
    object_schema => 'HR', object_name => 'EMPLOYEES',
    policy_name   => 'MASK_SALARY',
    function_schema => 'HR', policy_function => 'SALARY_COL_POLICY',
    statement_types => 'SELECT',
    sec_relevant_cols     => 'SALARY,COMMISSION_PCT',
    sec_relevant_cols_opt => DBMS_RLS.ALL_ROWS);  -- rows shown, salary NULL
END;
/
```

The policy function returns `'1=0'` for unauthorized roles; with `ALL_ROWS`, Oracle replaces the restricted columns with NULL for those users.

## Managing Policies

```sql
EXEC DBMS_RLS.ENABLE_POLICY('HR', 'EMPLOYEES', 'EMP_DEPT_VISIBILITY', TRUE);   -- enable
EXEC DBMS_RLS.ENABLE_POLICY('HR', 'EMPLOYEES', 'EMP_DEPT_VISIBILITY', FALSE);  -- disable (bypass!)
EXEC DBMS_RLS.DROP_POLICY('HR', 'EMPLOYEES', 'EMP_DEPT_VISIBILITY');
EXEC DBMS_RLS.REFRESH_POLICY('HR', 'EMPLOYEES');  -- force re-evaluation of cached predicates
```

> **Operational:** disabling a policy removes protection for every session — treat it as an approved change with a mandatory re-enable step. Multiple policies on one object AND together; use policy groups (`CREATE_POLICY_GROUP` + `ADD_GROUPED_POLICY` + `ADD_POLICY_CONTEXT`) for mutually exclusive, context-driven policies. There is no `DBMS_RLS.SET_CONTEXT` — group activation is driven by an application context value.

Inventory — *No dedicated tool — run via `oracle_execute_sql`:*

```sql
SELECT object_owner, object_name, policy_name, function,
       sel, ins, upd, del, enable, policy_type
FROM   dba_policies
ORDER  BY object_owner, object_name;
```

## Testing and Debugging

```sql
-- What predicate does the function produce for this session?
DECLARE
  v_predicate VARCHAR2(4000);
BEGIN
  v_predicate := hr.emp_dept_policy('HR', 'EMPLOYEES');
  DBMS_OUTPUT.PUT_LINE('Predicate: [' || v_predicate || ']');
END;
/
```

- Session context values — *No dedicated tool — run via `oracle_execute_sql`:* `SELECT namespace, attribute, value FROM session_context;`
- To see the rewritten SQL, trace the session (`EVENTS '10046 trace name context forever, level 12'`) and read the PARSE section of the trace file.
- Only `EXEMPT ACCESS POLICY` holders bypass VPD — keep that list to documented accounts (check via `oracle_dangerous_sys_privs`).

## Best Practices

1. **Set context via a logon trigger** — closes the window where unset context leaks everything or hides everything.
2. **Prefer STATIC / CONTEXT_SENSITIVE** policy types; DYNAMIC on busy tables becomes a bottleneck.
3. **Return `'1=0'` for missing context, never NULL** — default deny.
4. **`update_check => TRUE`** everywhere — prevents orphaned rows outside the visible window.
5. **No DML inside policy functions** — the kernel calls them during parse; DML causes recursive SQL and errors.
6. **Use plain views for simple static filters** instead of VPD.
7. **Document every policy** in the function — VPD is invisible to query writers.

## Common Mistakes and How to Avoid Them

**NULL context producing a broken or missing predicate** — always `IF v IS NULL THEN RETURN '1=0';` and cast context values (`TO_NUMBER`) to prevent predicate injection.

**Building predicates from raw user input** — only `SYS_CONTEXT` values (settable solely by the trusted package) are safe to concatenate; never concatenate application parameters into the predicate.

**DYNAMIC policy performance** — profile affected SQL before/after; if the function does lookups, index them and move to CONTEXT_SENSITIVE with a logon trigger.

**Views and synonyms inherit base-table policies** — adding policies to views over protected tables causes double filtering; design one enforcement point.

## Compliance Notes

- **HIPAA:** the "minimum necessary" standard — clinicians see only assigned patients; billing sees only billing fields.
- **PCI-DSS Req. 7:** cardholder tables restricted to the payment application's session context.
- **SOX:** entity-level isolation enforced at the data layer rather than duplicated in each application.

## Oracle Version Notes (19c vs 26ai)

- Baseline guidance is valid for Oracle Database 19c; `policy_type` constants are stable across 19c–26ai.
- For 26ai end-user/agent authorization, see `deep-data-security.md` — Deep Sec and VPD are different models; do not mix them in one design.
